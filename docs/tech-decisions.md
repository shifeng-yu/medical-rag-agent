# 技术决策记录（Tech Decisions）

本文件记录项目开发过程中的关键选型决策，说明"为什么这样做"而非仅"做了什么"。

---

## 1. 为什么不用 LangChain 直接搭，而是以 RAGFlow 图工作流为蓝本？

**背景**：项目需要双分支检索、条件分类、校验重试、失败回退的复杂流程。

**对比**：

| 方案 | 评估 |
|------|------|
| LangChain | 需要从零手写 DAG 调度与状态管理；其 LCEL 抽象在复杂分支/重试场景下调试成本高；私有化部署组件（知识库管理、文档解析）仍需自建 |
| LlamaIndex | 核心定位是 RAG 检索（索引/查询），Agent 流程编排能力弱；默认通用固定长度分块，医疗 Q&A 分块需从零开发 |
| RAGFlow（选用） | 原生 Q&A 分块模板 + 可视化图工作流，支持条件分支/重试；原生适配 Milvus，Docker 一键离线部署 |

**最终决策**：RAGFlow 承担**知识库管理与文档解析**（注册自定义分块插件 `ragflow_plugins/medical_qa_chunker.py`）；**问答主链路自研**（`src/core/workflow.py` 以其图编排为蓝本），一是为了完全可控、能精确复现工作流做 A/B 评测，二是本地量化推理与接口封装需要自己掌控。两者分工明确。

## 2. 重排序为什么分两阶段（粗排 + 精排）？

**背景**：双源检索（本地 KB + PubMed）共召回最多 20 条候选，若全部交给 BGE-M3 Cross-Encoder 精排，单次请求耗时不可接受。

**设计**（`src/core/reranker.py`）：

1. **粗排**：直接按 Milvus 向量相似度快速排序，截断到 top-K，将候选从 20 → 10 条
2. **精排**：对截断后的候选逐对计算 BGE-M3 Cross-Encoder 相关性分数，重排到 top-5
3. **来源加权**：精排分数叠加场景化来源权重（常见病优先本地指南 0.7/0.3，前沿问题优先文献 0.3/0.7），与问题分类结果联动

**效果**：平均响应 3.2s → 1.2s（串行检索改并行 + 两阶段重排），检索准确率较单库 baseline 提升 27%。

## 3. 量化为什么选 GPTQ INT4 而不是其他方案？

**背景**：Qwen-14B FP16 权重约 28G，目标是在单卡 12G 显存（RTX 3060）上完成全链路推理。

**对比**：

| 方案 | 评估 |
|------|------|
| GPTQ INT4（选用） | 权重量化到 4bit（28G→8G），配合 BGE-M3（1.2G）总占用 <10G；精度损失极小（实测准确率仅降 0.3%），无需重新训练 |
| AWQ | 同为 4bit 量化，精度略优但生态与 transformers 集成度当时不如 GPTQ 成熟 |
| FP16 直接部署 | 28G 显存需求，12G 单卡无法运行 |
| 蒸馏小模型 | 需要训练数据与算力，预研阶段成本过高；留作后续迭代方向 |

**实现**：加载职责收编于 `src/core/llm.py` 的 `QwenBackend`（懒加载至首次调用），同时支持 GPU（GPTQ 加载）与 CPU（标准 transformers 加载）双模式，架构代码不变，仅加载方式不同。切换后端（真实模型 / 测试用假话务员）只改 `settings.llm_backend`（`qwen` / `fake`），详见 [ADR-0003](adr/0003-llm-service.md)。

## 4. 会话记忆为什么用内存缓存 + 动态压缩？

**背景**：Qwen-14B 上下文窗口 8192，需留空间给检索文档与生成输出；多轮问诊历史会快速占满窗口。

**设计**（`src/session/manager.py`）：

- **短期记忆**：进程内字典缓存，key=session_id，24h TTL，用户间完全隔离
- **压缩触发**：token 数 > 2000 或轮次 > 4 时触发
- **压缩策略**：早期对话用大模型摘要（≤200 字），保留最近 4 轮完整对话

**效果**：上下文长度压缩 >70%，多轮问诊准确率仅降 0.8%。

> 预研阶段内存缓存满足需求；若正式落地，可将存储层替换为 Redis（接口已抽象，改动点集中在 session 模块）。

## 5. 基于 RAGFlow 复用的落地周期测算

**背景**：同类垂直领域 RAG 系统从零自建的成本评估，用于判断"框架复用 vs 自建"的选型收益。

**对比基准**：从零自建（自写 DAG 编排 + 通用分块 + 自建知识库管理/部署）vs 基于 RAGFlow 复用（可视化图工作流 + 原生 Q&A 分块 + 原生 Milvus 适配 + Docker 离线部署）。

**周期拆解**：

| 环节 | 自建（周） | RAGFlow 复用（周） | 省时原因 |
|------|-----------|-------------------|---------|
| 需求梳理与数据准备 | 1 | 1 | 相同，不省 |
| 分块与解析 | 2 | 0.5 | 原生 Q&A 分块模板，仅需调阈值/边界规则 |
| 检索链路（双源/重排） | 2 | 1 | 原生 Milvus 适配，免接口对接 |
| 工作流编排（分支/重试） | 2 | 0.5 | 可视化图工作流，拖节点即完成 |
| 部署与合规（私有化） | 1 | 0.5 | Docker 一键离线部署 |
| **合计** | **8** | **3.5** | — |

**结论**：落地周期从约 8 周缩短到约 3.5 周，**缩短约 60%**。此为基于选型对比的工程测算，用于支撑框架选型决策，非严格实测数据。
